1. EXECUTIVE SUMMARY & PRODUCT VISION
================================================================================

ClipLAN is a highly advanced, meticulously optimized, 100% serverless peer-to-peer (P2P) file sharing and real-time network clipboard application. In an era increasingly dominated by centralized cloud infrastructure—where data is frequently routed thousands of miles to a data center only to be downloaded by a device sitting three feet away—ClipLAN offers a radical return to true local networking. 

The primary product vision is to eliminate the latency, privacy risks, internet dependencies, and artificial bandwidth caps associated with cloud transfers. By heavily leveraging raw User Datagram Protocol (UDP) and Transmission Control Protocol (TCP) sockets, ClipLAN transforms standard mobile devices, laptops, and desktop computers into high-speed autonomous data servers. Devices running ClipLAN communicate directly with one another over the local router's subnet, operating at the absolute maximum bandwidth permitted by the physical hardware. Whether the environment is a high-speed corporate Wi-Fi 6 network pushing 100+ MB/s, or a direct Cat6 Ethernet link pushing gigabit speeds, ClipLAN scales dynamically to utilize the entire available pipe.

================================================================================
2. TECHNOLOGICAL FOUNDATION & JUSTIFICATION
================================================================================

Developing a reliable, cross-platform P2P engine requires a stack that can comfortably bridge low-level POSIX socket operations with high-level, responsive user interfaces. 

A. FLUTTER (UI FRAMEWORK)
Flutter was chosen because its rendering engine (Skia/Impeller) paints directly to the system canvas rather than relying on heavy native OEM widgets or slow WebViews. This ensures the application can render 60 to 120 Frames Per Second (FPS) smoothly, a critical requirement when attempting to animate progress bars and dynamic radar blips while the CPU is simultaneously decoding a 50GB file stream.

B. DART (PROGRAMMING LANGUAGE)
Dart serves as the backbone. Dart compiles Ahead-Of-Time (AOT) to raw ARM/x86 machine code. This is paramount because garbage-collected, interpreted languages often suffer from massive performance penalties and stuttering when handling heavy I/O operations. Dart’s `dart:io` library provides direct bindings to C-level network sockets, allowing ClipLAN to bypass high-level HTTP wrappers and directly manipulate raw TCP byte streams.

C. HIVE (NoSQL STORAGE)
For local database persistence, Hive was selected over SQLite. Hive is a lightweight, pure-Dart key-value store that operates entirely in memory while asynchronously syncing to disk. This allows for lightning-fast reads of the transfer history and settings without complex SQL join queries or asynchronous database locking delays.

D. SYSTEM INTEGRATIONS
- `wakelock_plus`: Prevents the operating system from arbitrarily putting the CPU to sleep during prolonged background file transfers.
- `crypto`: Powers the SHA-256 integrity verification pipelines.
- `permission_handler`: Manages complex runtime OS permissions across Android and iOS, specifically dealing with scoped storage and local network broadcasting permissions.

================================================================================
3. FLUTTER UI & REACTIVE STATE ARCHITECTURE
================================================================================

Unlike traditional REST-API driven web applications, ClipLAN operates essentially as a local server, meaning its state architecture must be heavily multi-threaded and completely decoupled from the UI thread to prevent UI lockups (jank).

3.1 THE MAIN ISOLATE & MVVM PATTERN
ClipLAN utilizes the `provider` package to implement a Model-View-ViewModel (MVVM) architecture. The central brain of the UI is `AppState` (the ViewModel), which extends `ChangeNotifier`. The UI components (the Views) merely observe this state. When a file is transferring, the TCP background engine continuously increments a `bytesTransferred` integer. The engine then throttles UI updates to fire roughly every 50 milliseconds by calling `notifyListeners()`. The Flutter tree detects this state change and strictly rebuilds only the `LinearProgressIndicator` widget inside the `TransferCard`, completely ignoring the rest of the application tree. This surgical rebuilding is what allows the app to feel incredibly lightweight, even under extreme load.

3.2 BACKGROUND WORKERS (ISOLATES)
To maintain the 60 FPS guarantee, expensive operations are pushed to separate CPU threads known as Isolates. For example, when a user navigates to the File Browser screen, ClipLAN must traverse the Android/iOS file system to generate lists of Images, Videos, and Documents. If this directory traversal occurred on the main thread, the app would freeze for several seconds. By utilizing Isolates, the OS traverses the disk asynchronously, allowing the user to smoothly scroll the UI while the files lazily load in.

================================================================================
4. NETWORKING SUBSYSTEM A: THE DISCOVERY ENGINE (UDP)
================================================================================

The cornerstone of a serverless application is its ability to find peers without a central directory. ClipLAN accomplishes this via a highly resilient UDP broadcasting protocol.

4.1 THE MULTI-CAST HEARTBEAT
The Discovery Engine binds a `RawDatagramSocket` to UDP Port 53317. Every 2 seconds, a timer fires, executing a "Heartbeat" function. This function constructs a tiny JSON payload containing the device's UUID, user-defined name, platform type (Android/iOS/macOS), and the dynamic TCP port it is currently listening on.
This packet is simultaneously blasted to:
- The Global Broadcast IP: `255.255.255.255`
- The Local Subnet Broadcast IP (e.g., `192.168.1.255`)
- Multicast Groups: `224.0.0.1` and `224.0.0.251`

4.2 UNICAST LASER-BEAM HANDSHAKES
Corporate networks, university campuses, and strict home routers often implement "Client Isolation" or aggressively drop broadcast packets to reduce network noise. To combat this, ClipLAN implements a "Unicast Handshake". If Device A manages to hear even a single broadcast from Device B, Device A immediately extracts Device B's source IP address from the packet. Device A then fires a direct, unicast UDP response straight to Device B. Because routers do not block targeted unicast traffic, the devices successfully register each other instantly, bypassing the broadcast firewall entirely.

4.3 RESILIENT GARBAGE COLLECTION
Wireless networks are notoriously unstable; packets drop frequently. If ClipLAN removed a device from the screen the moment a packet was missed, the UI would flicker maddeningly. Instead, a Garbage Collection loop runs every 3 seconds, evaluating the timestamp of the last received packet from every known peer. A device is only culled from the UI if it fails to send a packet for 15 consecutive seconds, ensuring a highly stable user experience.

================================================================================
5. NETWORKING SUBSYSTEM B: THE TRANSFER ENGINE (TCP)
================================================================================

While UDP is excellent for broadcasting presence, it does not guarantee delivery. For actual file transfer, a reliable, ordered stream is required. ClipLAN utilizes a bespoke TCP streaming engine operating on port 53318 (with ephemeral fallbacks if the port is busy).

5.1 THE HANDSHAKE & APPROVAL PHASE
When User A taps "Send", a TCP connection is opened to User B. User A sends a length-prefixed `transfer_request` JSON control packet containing the file metadata (names, sizes, types). User B's device catches this packet, pauses the stream, and throws up an `approval_sheet` modal UI. If User B taps "Reject", a boolean `false` is returned, and both sockets are gracefully closed. If "Accept" is tapped, the binary pipeline opens.

5.2 ZERO-COPY STREAMING (THE MAX SPEED ALGORITHM)
Historically, poorly written file transfer apps load massive chunks of a file into RAM before sending them to the socket, or conversely, read massive chunks from the socket into RAM before saving to disk. This causes catastrophic Out-Of-Memory (OOM) crashes on low-end devices.

ClipLAN implements a Zero-Copy stream architecture using `streamBytesTo`. The engine treats the Flutter application merely as a traffic controller. The operating system kernel pulls raw binary byte arrays directly off the Network Interface Card (NIC) and funnels them directly into the physical disk controller (`IOSink.add`). The bytes effectively bypass the Dart Virtual Machine's garbage collector, completely eliminating memory allocation overhead.

5.3 DYNAMIC OOM BACKPRESSURE & FLUSHING
A severe hardware limitation occurs when the Wi-Fi speed dramatically outpaces the Disk Write speed. If an iPad is receiving data over Wi-Fi 6 at 80 MB/s, but its internal storage can only physically write at 20 MB/s, the operating system is forced to buffer the remaining 60 MB/s in the device's RAM. Over a 5-minute transfer, this buffer explodes to several gigabytes, inevitably causing the OS to forcibly crash the app.

ClipLAN dynamically prevents this using a backpressure tracking algorithm. It continuously monitors the exact number of bytes piped to the disk. The exact millisecond this buffer crosses a 10 Megabyte threshold, ClipLAN commands the disk sink to `await sink.flush()`. This command synchronously blocks the network socket from reading any more data off the Wi-Fi chip until the physical disk successfully flushes the buffer to the permanent storage platters. Once flushed, the network socket is instantly un-paused (`_subscription?.resume()`). This creates a perfectly stable, undulating pipeline where RAM usage remains flat indefinitely, theoretically allowing ClipLAN to transfer a 1-Terabyte file on a device with only 2 Gigabytes of RAM.

================================================================================
6. CRYPTOGRAPHIC DATA INTEGRITY & VALIDATION
================================================================================

Data corruption is a very real threat over unstable wireless mediums. ClipLAN utilizes the SHA-256 (Secure Hash Algorithm 256-bit) to guarantee mathematical perfection of all transmitted files.

6.1 PRE-CALCULATION & TRANSMISSION
Before the TCP engine begins streaming binary data, the sender's device scans the local file and calculates its SHA-256 digest. This 64-character hexadecimal string is injected into the `file_start` JSON control frame and sent to the receiver.

6.2 CHUNKED CONVERSION
Because the files can be gigabytes in size, the receiver cannot wait for the file to finish downloading to load it into memory and hash it. Instead, ClipLAN utilizes a `sha256.startChunkedConversion()` sink. As the Zero-Copy TCP stream pipes blocks of data to the hard drive, it simultaneously duplicates those blocks into the cryptographic sink in real-time. 

6.3 FINAL VALIDATION
The moment the final byte of the file is written, the cryptographic sink emits the final calculated hash. ClipLAN compares this calculated hash against the expected hash provided in the `file_start` packet. If they match identically, a `file_ack` control packet is dispatched to the sender marking success. If they differ, the file is immediately marked as corrupted and deleted, ensuring the user is never left with a broken file.

================================================================================
7. STORAGE, PERSISTENCE, & THE HISTORY ENGINE
================================================================================

ClipLAN maintains a comprehensive historical ledger of all network activity, backed by a Hive NoSQL database. 

7.1 THE FILE PATH SERIALIZATION FIX
A major architectural challenge in file sharing is the "Retry" mechanic. If a transfer fails halfway through, the user expects to be able to tap "Retry" and try again. However, if the app restarted, it would forget where the file actually lived on the local file system. ClipLAN solves this by heavily serializing the absolute physical `path` of every file into the `HistoryBox`. 

7.2 THE RECENTS ALGORITHM
This robust path serialization spawned the "Recents" functionality. When a user opens the File Browser, ClipLAN queries the Hive database, extracts the physical paths of all files transferred in the last 7 days, cross-references those paths with the operating system to verify the files haven't been deleted or moved by the user, and dynamically populates a "Recents" grid. This allows for lightning-fast re-sharing of frequently sent documents.

================================================================================
8. HARDWARE INTERACTION & WAKELOCK STABILITY
================================================================================

Transferring heavy 4K videos or operating system images can take several minutes. Mobile operating systems (iOS and Android) are aggressively optimized for battery life. If a user puts their phone face down and the screen turns off, the OS will aggressively suspend the CPU and tear down active TCP sockets, instantly killing the transfer.

To combat this, ClipLAN integrates deep hardware control via the `wakelock_plus` package. The `TransferService` maintains an internal `_activeTransferCount`. The moment a TCP socket is opened and data begins flowing, this count increments, and a hardware Wakelock is acquired. This explicitly instructs the OS kernel to keep the CPU awake and the Wi-Fi radio powered at maximum voltage, even if the screen turns off. The moment the transfer count hits 0 (whether through success, cancellation, or failure), the Wakelock is safely released, returning the device to its normal power-saving state.

================================================================================
9. OPERATING SYSTEM SANDBOXING & PERMISSIONS
================================================================================

Different operating systems require vastly different security architectures.

9.1 ANDROID SCOPED STORAGE
Android enforces Scoped Storage, heavily restricting where apps can write files. ClipLAN utilizes the `path_provider` to securely locate the public `Downloads` directory, ensuring that received files are immediately visible to the user in their standard gallery and file manager apps, without requiring complex root access.

9.2 MACOS APP SANDBOX ESCAPE
macOS utilizes a strict App Sandbox that restricts applications to their own tiny hidden container folder. To allow ClipLAN to be a true desktop-class application, the Sandbox had to be intentionally broken. In the Xcode configurations (`DebugProfile.entitlements` and `Release.entitlements`), the `com.apple.security.app-sandbox` key is explicitly set to `false`. This architectural decision grants ClipLAN global POSIX permission to read from the Desktop, Documents, and external hard drives, and write received files directly to the global user Downloads folder without throwing `EACCES` (Permission Denied) errors.

10. COMPREHENSIVE USE CASES & I/O MAPPING
================================================================================

USE CASE 1: SHARED NETWORK CLIPBOARD
- Input: User types a URL into the Shared Clipboard text box and hits enter.
- Processing: App wraps the string in a UDP `clipboard` JSON packet and broadcasts it.
- Output: Every phone in the room receives the packet. A Snackbar pops up on their screen offering a one-tap copy button to inject the text directly into their system clipboard.

USE CASE 2: MASSIVE FILE TRANSFER
- Input: User selects a 5GB `.mp4` video from their gallery.
- Processing: App hashes the file, opens a TCP socket, gets recipient approval, and initiates a Zero-Copy byte stream. The dynamic flush algorithm engages 500 times (every 10MB) to protect RAM.
- Output: 5GB file lands perfectly on the recipient's hard drive. Both UI screens show a "Completed" badge. Wakelock is released.

USE CASE 3: CANCELLATION EVENT
- Input: User gets impatient and hits the "X" button mid-transfer.
- Processing: The UI fires a cancellation event. The `TransferService` catches this, forcefully tears down the active TCP socket, aborts the `IOSink` stream, and throws a controlled exception.
- Output: The status immediately changes to `TransferStatus.failed`. The partial, corrupted file on the recipient's device is cleanly deleted from the disk to prevent space leaks.

Every nook and cranny—from the surgical UI repaints, to the unicast firewall-bypassing handshakes, to the dynamic OOM backpressure pipelines—has been engineered for absolute maximum performance and bulletproof stability.





# ClipLAN Application Documentation
## Comprehensive Technical Overview

1. INTRODUCTION AND MAIN FUNCTIONALITY
================================================================================

ClipLAN is a blazing-fast, decentralized, offline, peer-to-peer (P2P) file and clipboard sharing application built primarily to solve the bottleneck of transferring large files or text snippets between devices over local networks. The app is completely serverless, meaning it relies solely on the Local Area Network (LAN) or a mobile hotspot to communicate. By eliminating the cloud from the equation, ClipLAN achieves data transfer speeds limited only by the hardware limitations of the network interface cards (NIC) and Wi-Fi routers involved. 

### Focus on Android and iOS Capabilities
On mobile platforms (Android and iOS), the app focuses heavily on the seamless user experience. 
- **Android Capabilities**: Android users can take advantage of deep system integration using the `receive_sharing_intent` plugin, allowing users to select files directly from their gallery or file manager and share them instantly to ClipLAN. They can also use Wi-Fi Direct and Hotspot APIs for environments where no router is present. Furthermore, Android allows Background Services to keep transfers alive when the app is minimized (handled by wakelocks).
- **iOS Capabilities**: Due to iOS sandboxing, the app heavily relies on the `file_picker` to grant the application temporary read access to the Apple Files app and Photos Library. On iOS, the app leverages the Local Network Privacy permissions to perform UDP broadcasts. Clipboard sharing on iOS is highly restricted to foreground processes, so the app synchronizes clipboard states precisely when the user brings the app back to the foreground.

### Key Features
1. **P2P File Transfer:** No file size limits. Data flows directly from one IP address to another via a TCP socket.
2. **Cross-Platform Clipboard Synchronization:** Instantaneous text sharing between devices. A copied text snippet on an Android phone can immediately populate the clipboard of an iOS or macOS device on the network.
3. **QR Code Connection:** If UDP broadcasting fails due to complex network topologies (like enterprise networks blocking subnet broadcasts), devices can manually pair using QR codes containing the IP and port metadata.
4. **Offline First:** Zero internet reliance ensures absolute data privacy.

2. TECHNOLOGY STACK
================================================================================

The technological foundation of ClipLAN is optimized for cross-platform compatibility, real-time socket communication, and performant UI rendering.

*   **Frontend / Core Framework**: Flutter (Dart)
    *   *Why?* Allows a single codebase to compile natively to Android (Kotlin/C++), iOS (Swift/Objective-C), macOS, Windows, and Linux.
*   **Networking Layer**: Raw Dart `dart:io` Sockets
    *   *Why?* Maximum throughput. We use `RawDatagramSocket` for UDP broadcasts and `ServerSocket`/`Socket` for TCP data streaming.
*   **State Management**: Provider (ChangeNotifier)
    *   *Why?* Offers an excellent balance of simplicity and performance. It allows deep widget trees to reactively rebuild only when specific application states (like transfer progress) change.
*   **Local Storage**: Hive (NoSQL Key-Value Store)
    *   *Why?* Hive is written in pure Dart and is incredibly fast. It operates synchronously, which makes reading application settings, transfer histories, and saved clipboards practically instantaneous.
*   **Design Language**: Custom Glassmorphism UI
    *   *Why?* Rather than adhering strictly to Material (Google) or Cupertino (Apple) guidelines, ClipLAN employs a futuristic, blurred, translucent UI architecture that looks premium on both mobile and desktop platforms.

================================================================================
3. SYSTEM DESIGN AND ARCHITECTURE
================================================================================

ClipLAN's architecture follows a classic Model-View-ViewModel (MVVM) inspired structure, loosely coupled via dependency injection (Provider). 

### The Network Topology
The system operates on a decentralized mesh topology. Every instance of ClipLAN acts as both a **Client** and a **Server**. 
1.  **Server Daemon**: Upon startup, the app spins up a TCP Server on a randomized port (or fixed if specified) to listen for incoming file and clipboard streams.
2.  **UDP Announcer**: Concurrently, it spins up a UDP broadcast socket. It shouts an "I am here" JSON payload to the `255.255.255.255` broadcast address at regular intervals.
3.  **The Handshake**: When Device B hears Device A's UDP broadcast, it reads Device A's IP and TCP port. If Device B wants to send a file to Device A, it opens a direct TCP connection to Device A's IP:Port. 
4.  **Payload Exchange**: The TCP stream is opened. The sender writes a JSON header (containing filename, size, type, and SHA-256 hash). A delimiter is sent, followed by the raw binary bytes of the file in chunks. The receiver parses the header, allocates file space, and writes the incoming bytes to the disk directly using `IOSink` to prevent RAM overflow.

================================================================================
4. THE 5 CORE MODULES
================================================================================

The application is strictly divided into 5 independent, highly cohesive modules.

### Module 1: The Discovery Module (`discovery_service.dart`)
**Purpose**: Responsible for finding other devices on the local network.
**How it Works**: 
This module leverages `RawDatagramSocket`. It binds to a specific UDP port (e.g., 53317). It runs a periodic timer (every 2-3 seconds) that serializes the device's metadata (Username, OS, Device ID, TCP Port) into a UTF-8 JSON string and broadcasts it over the subnet. Simultaneously, it listens for incoming datagrams. When a datagram is received from an external IP, it deserializes the payload, constructs a `DeviceInfo` object, and yields it to a Stream. It manages a cache of active devices, aging out devices that haven't broadcasted in the last 15 seconds.

### Module 2: The Transfer Module (`transfer_service.dart`)
**Purpose**: Handles the heavy lifting of raw data transmission.
**How it Works**:
This module utilizes `ServerSocket` and `Socket`. When initialized, it binds a TCP server to `InternetAddress.anyIPv4`. 
*   **Sending**: When a user selects a file, this module establishes a TCP client connection to the target device. It computes the SHA-256 hash of the file asynchronously. It creates a structured payload: a header containing `{ "type": "file", "name": "...", "size": X, "hash": "..." }`, followed by a `


` delimiter, and then pipes the file stream directly into the socket using `File.openRead().pipe(socket)`.
*   **Receiving**: The `ServerSocket` listens for `Socket` connections. When a connection is accepted, it buffers the incoming bytes until it finds the `


` delimiter. It parses the JSON header to understand what is coming. If it's a file, it opens an `IOSink` to the device's Downloads directory and writes the remaining byte stream to the disk in real-time. It reports progress by comparing `bytesReceived` against the `size` specified in the header.

### Module 3: The State Management Module (`app_state.dart`)
**Purpose**: The central brain connecting the UI to the background services.
**How it Works**:
Extending `ChangeNotifier`, this module holds the current state of the application. It instantiates the `DiscoveryService` and `TransferService`. It listens to their streams. When the `DiscoveryService` finds a new device, it updates the `availableDevices` list and calls `notifyListeners()`, which instantly updates the radar animation on the UI. It manages the queue of active transfers, tracking their progress (0.0 to 1.0), speed (MB/s), and status (pending, transferring, completed, failed). It is also responsible for bridging the `Clipboard` API with the `TransferService` to send text snippets as special TCP payloads.

### Module 4: The Storage & Persistence Module (`storage_service.dart` + Hive)
**Purpose**: Ensuring data survives app restarts.
**How it Works**:
Before the Flutter engine renders the first frame, Hive is initialized. It opens several binary boxes (e.g., `settingsBox`, `historyBox`, `clipboardBox`). The `StorageService` acts as a repository pattern wrapper around Hive. When a transfer completes successfully, the State Management module sends a `TransferItem` object to the `StorageService`. The service saves this to the `historyBox`. When the app cold-starts, it reads this box to populate the History Screen. It also stores user preferences like their custom username, dark mode settings, and default save directories.

### Module 5: The User Interface (UI) Module (`screens/` and `widgets/`)
**Purpose**: The visual layer users interact with.
**How it Works**:
Built entirely in Flutter, this module observes the State Management module. 
*   `devices_screen.dart` renders a beautiful radar pulsing animation (using `CustomPainter` and `AnimationController`) to visually represent the network search.
*   `transfer_card.dart` uses `LinearProgressIndicator` bound to the active transfer's progress value to show real-time completion status.
*   The UI makes heavy use of `BackdropFilter` to achieve the glassmorphic blur effects over animated backgrounds, ensuring the app feels native, fluid, and premium on iOS and Android.

5. DEPENDENCY INJECTION & EXTERNAL LIBRARIES
================================================================================

ClipLAN avoids reinventing the wheel by leveraging robust community dependencies listed in `pubspec.yaml`:

1.  **`provider`**: The core state management library. It injects the `AppState` at the root of the widget tree so any nested widget can read or manipulate the application state without passing callbacks down multiple layers.
2.  **`hive` & `hive_flutter`**: A lightweight, incredibly fast NoSQL database. Chosen over SQLite because P2P apps require extremely fast, synchronous read/writes for settings and history logs without the overhead of SQL queries.
3.  **`file_picker`**: Crucial for cross-platform file selection. It interfaces with the Android Storage Access Framework (SAF) and the iOS Document Picker/Photos library, returning abstract `PlatformFile` objects that the app can read from.
4.  **`path_provider`**: Resolves the complex directory structures of different operating systems. It tells the app where the "Downloads" or "Application Documents" directories are located securely on iOS and Android.
5.  **`crypto`**: Used to generate SHA-256 hashes of files before they are sent, and re-hashing them upon receipt to guarantee data integrity over the network.
6.  **`uuid`**: Generates unique identifiers for devices and individual transfer sessions, preventing collisions if two files with the same name are sent simultaneously.
7.  **`mobile_scanner` & `qr_flutter`**: Powers the manual QR code connection system. `qr_flutter` renders the IP/Port payload as a scannable graphic, while `mobile_scanner` accesses the device camera to decode it.
8.  **`receive_sharing_intent`**: Deep OS integration for Android/iOS. Allows users to "Share" a file from their phone's native gallery directly into ClipLAN, intercepting the intent bundle and triggering the transfer logic automatically.
9.  **`wakelock_plus`**: Essential for mobile devices. It prevents the CPU and screen from going to sleep during a long multi-gigabyte file transfer.
10. **`open_filex`**: Provides the ability to tap on a completed transfer in the History screen and have the native OS open it in the default application (e.g., opening a received `.mp4` in VLC or the native video player).

6. DETAILED FILE CONTRIBUTIONS (CODEBASE BREAKDOWN)
================================================================================

To understand how the app functions, one must examine the responsibility of each specific file in the `lib/` directory.

### `/models/` Directory
The blueprint of the application's data.
*   **`device_info.dart`**: Contains the `DeviceInfo` class. This defines what a "Peer" looks like: String id, String name, String os, String ip, and int port. It includes `fromJson` and `toJson` methods for UDP serialization.
*   **`transfer_item.dart`**: The model representing an active or completed transfer. It holds the file name, size, speed, progress, sender/receiver details, and status enums (`Pending`, `Transferring`, `Completed`, `Failed`).
*   **`clipboard_item.dart`**: A simple wrapper representing a synchronized string of text, complete with timestamps and origin device info.

### `/providers/` Directory
*   **`app_state.dart`**: The monolith orchestrator. It holds lists of `DeviceInfo` and `TransferItem`. It handles the logic of "User tapped send -> Start file picker -> Get path -> Call TransferService.sendFile()". It listens to the `ReceiveSharingIntent` streams and automatically starts transfers when external intents are caught.

### `/screens/` Directory
*   **`home_screen.dart`**: The main navigation hub, usually a `Scaffold` with a `BottomNavigationBar` connecting to the other screens.
*   **`devices_screen.dart`**: The flagship UI component. It displays the radar animation. It lists discovered devices via a `ListView.builder`. Tapping a device opens an action sheet (Send File / Send Clipboard).
*   **`file_browser_screen.dart`**: A custom interface to view the internal storage and app-specific directories, allowing users to manage received files natively within the app.
*   **`clipboard_screen.dart`**: Displays a history of received clipboards. It features a text input field to manually type and broadcast text to connected devices.
*   **`history_screen.dart`**: A list of all historical transfers loaded from Hive. Features progress bars for ongoing transfers and "Open File" buttons for completed ones.
*   **`settings_screen.dart`**: Allows the user to change their display name, toggle dark mode, specify fixed TCP ports, and wipe the database history.
*   **`qr_scanner_screen.dart`**: A full-screen camera view wrapping `mobile_scanner` to decode fallback QR connections.

### `/services/` Directory
The background workers doing the heavy OS-level interactions.
*   **`discovery_service.dart`**: Handles `RawDatagramSocket`. Core functions: `startBroadcasting()`, `startListening()`, `stop()`.
*   **`transfer_service.dart`**: Handles `ServerSocket` and `Socket`. Core functions: `startServer()`, `sendFile(File, TargetIP)`, `sendClipboard(Text, TargetIP)`. Manages the complex byte chunking and JSON header protocol.
*   **`storage_service.dart`**: The Hive wrapper. Core functions: `saveTransfer()`, `getTransfers()`, `updateSettings()`.
*   **`rate_limiter.dart`**: A small utility class to prevent the UI from choking. When downloading at 500 MB/s, calling `notifyListeners()` on every byte chunk would freeze the Flutter rendering thread. The rate limiter ensures UI progress updates only happen every 50-100 milliseconds.

### `/widgets/` Directory
Reusable, decoupled visual components.
*   **`radar_animation.dart`**: A highly optimized `CustomPainter` that draws concentric expanding circles, mathematically calculating opacities based on animation controllers to simulate a sonar ping.
*   **`transfer_card.dart`**: A sophisticated list tile that changes color based on the transfer status, containing a `LinearProgressIndicator` and speed/ETA text calculations.
*   **`glassmorphic_card.dart`**: A wrapper widget utilizing `BackdropFilter(filter: ImageFilter.blur(sigmaX: 10, sigmaY: 10))` wrapped in a `ClipRRect` to give the app its signature translucent aesthetic.
*   **`hashing_dialog.dart`**: An indeterminate loading modal displayed when the app is computing the SHA-256 hash of a massive file before the network transfer begins, preventing the user from thinking the app has frozen.
